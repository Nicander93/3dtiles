# 并发可靠性、处理性能与暂停续跑：技术方向计划

日期：2026-09-21

状态：方向规划，尚未实施。

依据：本地产品仓库 `master@8c84bb2`；相邻 `D:/code/geoforge-converter` 的当前源码只读检查。未在本轮重新 fetch，也未证明相邻源码与安装版 converter 二进制一致。

本文独立规划下一阶段开发，承接 `06-v1-convergence-execution-plan.md`。并发、性能、暂停续跑的后续方向以本文为准；06 的正确性、输出安全、格式校验及安装验收要求继续适用。本文替代其第 11 节作为后续规划入口，不沿用收敛计划的工期估算。

## 1. 要达到的使用体验

1. 用户选择并发数后确实生效，同一份数据在多 worker 下稳定处理。
2. 能看到哪个阶段耗时、完成了多少工作、是否发生重试；性能改进有测量结果。
3. 长任务支持在安全边界暂停，继续后不重复已经确认完成的工作。
4. 关闭应用或异常退出后，在输入、参数和运行时兼容的前提下，从有效检查点继续。

首要目标是单任务可靠提速。多个桌面任务同时运行后置；首版暂停与细粒度续跑优先覆盖 OSGB 转换，其他阶段分批支持。

## 2. 从当前代码出发

| 当前位置 | 已有实现 | 对新计划的影响 |
| --- | --- | --- |
| `crates/processor/src/stages/convert.rs` | 读取线程配置；首次调用 `run_native` 传 `None`；部分故障清理转换输出后单线程重试 | 先修复参数，再测真实并发；重试成功不能掩盖首次失败 |
| `apps/desktop/src-tauri/src/settings_store.rs` | 设置写入 SQLite JSON；没有前端使用的默认并发字段 | 补字段、旧 JSON 默认值及持久化验证 |
| converter 的 `src/osgb.rs` | `osgb_batch_convert` 枚举 `Data/Tile_*`；Rayon 按顶层 Tile 调用 C++ 入口；全部并行调用结束后接收并汇总结果 | 顶层 Tile 是第一版工作单元候选；需改成边完成边汇总/持久化 |
| `crates/top_rebuild/src/tileset_writer.rs` | `rebuild_tileset` 按层遍历，层内逐节点构建 Proxy，并修改共享 payload/metrics | 可评估同层有限并行，先生成独立节点结果再汇总，不能直接给循环加并行迭代 |
| `crates/processor/src/pipeline.rs` | scan→convert→rebuild→texture→validate→commit；临时目录中逐阶段运行 | 保留阶段编排，增加可复用阶段结果与恢复入口 |
| `crates/processor/src/stages/commit.rs` | 临时目录独占创建、归属 marker、取消清理、最终 no-replace rename | 恢复须有独立的受控打开入口，不能去掉现有目录拒绝规则 |
| `crates/processor/src/cancel.rs` | 原子取消标志；stdin 识别取消消息 | 需要真正的控制命令解析与暂停状态，不能复用取消表示暂停 |
| `crates/protocol/src/lib.rs` | TaskConfig v1、阶段、成功/失败/取消退出码 | 增加版本化控制与事件契约，定义暂停确认和可恢复状态 |
| `apps/desktop/src-tauri/src/process_manager.rs` | 单任务调度、子进程 stdin、Job Object、关闭时终止并标记 interrupted | 可复用通信与进程清理；暂停后的退出和状态归档需单独设计 |
| `task_store.rs`、`Processing.tsx`、`api/types.ts` | 持久任务记录、现有状态和取消操作；无 paused/resuming | 后端能力完成后再接状态显示与按钮 |

当前没有暂停/恢复实现，也没有可靠的 Tile 完成检查点。`interrupted` 表示任务中断，不表示可以继续计算。已有临时输出和历史任务记录不能直接视作检查点。

## 3. 推荐的总体方向

保持现有分层，在处理工具内建立“有界派发、独立工作单元、完成记录、单一汇总”的执行方式。

```text
Desktop：用户操作、任务记录、状态展示
    ↓ 控制命令 / ↑ 事件和确认
Processor：阶段编排、工具能力检查、恢复校验、最终提交
    ↓ 受控启动与工具协议
Converter：Tile 工作队列 → 有限 worker → 已校验完成记录 → 根 tileset 汇总
TopRebuild：按依赖逐层推进 → 同层有限 worker → 节点完成记录 → 树与指标汇总
```

Converter 负责 Tile 细节和原生处理；Processor 不重新实现 OSGB 转换算法。Desktop 不承担 worker 调度与文件有效性判断。

完成记录由实际执行工具产生，Processor 负责验证和引用。SQLite 保存任务状态及检查点位置等摘要；完整单元清单优先保存在任务工作目录，避免桌面数据库成为算法进度的唯一依据。

这只是实施方向，文件格式、API 名称、协议版本与存储粒度在小样原型验证后确定。

## 4. 阶段 A：参数正确、故障可复现

这是首批实施范围，应与原计划 R01/R02 合并执行，避免重复修改。

### A1. 修复实际线程设置

- 把配置传到首次 converter 调用；明确缺省、自动、固定线程数和环境变量的优先级。
- 自动模式不能因继承环境变量意外变成固定线程数；实际 worker 数以 converter 日志/事件为依据。
- 补齐默认并发设置持久化和旧设置读取兼容；新安装默认 keep + 1 worker。
- 测试真实子进程收到的参数，而不仅测试配置解析函数。

### A2. 建立并发诊断基线

- 固定 converter 源码、二进制、依赖版本、数据、坐标与纹理参数；不能直接用相邻仓库源码解释不同版本的安装包崩溃。
- 用相同样本对比 1/2/4/8 worker，先小样重复，再真实大样；分别统计首次失败率、重试次数和总耗时。
- 在 Tile 开始/结束记录单元 ID、阶段、耗时、线程/worker；保留原生崩溃 dump 和 stderr。
- 测量 scan、convert、rebuild、texture、validate、commit 的时间，至少记录进程峰值内存与输入/输出体积；有条件时记录 CPU、磁盘和实际线程数。

验收：线程设置真实生效；失败能定位到版本、数据和工作单元；可以判断慢在转换、重建、纹理、I/O，还是失败后的整段重跑。

## 5. 阶段 B：修复转换器并发，再建立有界调度

### B1. 依据证据选择线程或进程方案

优先检查当前 `Rayon → osgb23dtile_path` 路径的共享状态、初始化、库调用重入、对象生命周期和写入冲突。这些均为待验证假设，不是已确认的崩溃原因。

| 证据 | 优先处理方向 |
| --- | --- |
| 少量全局状态或初始化竞争 | 将状态移入任务/worker，或只同步确需串行的初始化/共享操作 |
| 可定位的对象生命周期、内存错误 | 修复正确性缺陷，再重跑并发压力测试 |
| 必须使用不可重入库，线程隔离成本过高 | 原型验证有限多进程 worker，比较启动、内存、吞吐与崩溃隔离收益 |
| CPU/内存/磁盘过度争用 | 限制在途任务和内部线程，建立资源预算 |

不先选全局大锁，也不先全面改多进程。当前 `_3dtile` 是整数据集入口，多进程方案需要增加明确的单元处理契约、坐标上下文和汇总入口，不能同时启动多个整库任务写同一输出目录。

### B2. 演进现有 Tile 循环

- 第一版单元定义为 `Data` 下一个顶层 Tile 的完整转换子树，以现有入口和结果结构为起点。
- 在派发前检查取消、暂停请求和资源额度；执行中单元数量受控。
- worker 返回独立结果；汇总方边接收边验证与记录，最后统一生成根 tileset。
- 当前代码在 `pool.install` 结束后才消费 receiver；若改为有界通道，必须同时消费或改写收集流程，否则可能阻塞整个池。
- 进度以已确认完成单元计数，Tile 大小不同导致百分比不等于剩余时间；没有可靠估算时不显示虚假 ETA。
- 原始错误与重试分开记录。只有在单元隔离和输出有效性得到保证后，才把“整次转换重跑”优化为“失败单元重跑”。

验收：触发样本在修复后通过多线程重复测试；失败无伪成功；同目录无并发写入冲突；峰值内存可控；质量与单线程基线一致。

## 6. 阶段 C：按测量结果优化吞吐

### 转换

对比 worker 数、CPU 利用率和 I/O，检查外层并行与编码器内部线程叠加。选择能稳定提高端到端吞吐的默认上限；不要以 CPU 占满作为唯一成功标准。

顶层 Tile 粒度可能出现长尾：一个 Tile 内含大量子节点，其余 worker 已空闲。如果基线证明确有影响，再考虑拆细该 Tile；拆细之前必须厘清输出与坐标依赖，不提前重写整个转换内核。

### 顶层重建

当前逐层、层内串行结构可演进为：读取上一层已完成 payload → 构建本层不可变任务输入 → 有限并行生成节点结果 → 顺序合并 payload、warnings、metrics → 推进下一层。

只并行依赖已经满足的节点；限制同时解码的大几何和纹理数量。先确认 `build_proxy_to_file` 及其编码/临时文件路径具备并行条件。禁止并发修改现有共享 map 和聚合指标。

### 纹理、复制与校验

仅在数据表明它们是主要瓶颈时优化。可评估文件级有限并行、避免重复解码、减少额外复制；保留独立输出和最终提交，不通过修改输入或不安全覆盖换取速度。

验收：同一数据、同缓存条件至少多次测量，报告中位耗时、波动、峰值内存、失败率和质量。取得基线后再定速度目标，不提前承诺“快几倍”。

## 7. 阶段 D：先实现转换检查点

建议先做到“已完整转换的 Tile 可以复用”，再向其他阶段扩展。

### D1. 完成记录

每个记录至少包括：工作单元 ID、源输入指纹、输出清单及有效性证据、参数指纹、坐标上下文、converter 版本/hash、格式版本、状态，以及根汇总需要的 Tile JSON 与 bounds。

只保存 `.b3dm` 文件不足以恢复：当前 converter 还依赖内存中的 TileResult 汇总根文件，因此这部分结果也必须持久化并校验。

输入指纹策略需要明确可信度：路径/大小/mtime 可以用于快速筛查，不能单独证明内容未改变。为正确性要求高的复用采用内容摘要或等效验证，并测量其成本。

### D2. 写入与恢复

- 单元先写临时位置，完成校验并发布单元输出后，原子更新完成记录；只有已确认完成状态可复用。
- 记录损坏或输出缺失时该单元重做；输出存在但没有可靠记录时不自动跳过。
- 检查点有 schema 版本；源数据、参数或工具不兼容时拒绝复用或精确失效下游，向用户说明需重算的范围。
- 最终根 tileset 由有效单元重新汇总，仍经完整校验后才发布最终成果。
- 为 `commit.rs` 增加受控恢复入口：校验 marker、任务归属、工作目录和独占执行锁。普通新任务继续拒绝占用已有临时目录。
- 暂停/可恢复中断保留工作目录；取消清理和保留策略明确区分。UI 展示占用空间并提供明确的丢弃入口。

验收：在单元写入、输出发布、记录提交和根汇总之间注入崩溃，恢复后只重做未确认单元；半成品不被当作完成；不修改输入或覆盖既有成果。

## 8. 阶段 E：接入暂停、继续和重启续跑

推荐第一版采用“安全落盘后退出、继续时重新启动并恢复”的暂停方式。这样暂停不长期占用 worker 与内存，并与关闭应用后的续跑共用恢复路径。正式采用前先用转换阶段原型验证开销与协议。

拟定状态过程：

```text
running → pausing → paused → resuming → running
running / pausing 意外退出 → interrupted → 验证检查点 → resuming
```

### 控制与确认

- Desktop 向 Processor 发送有结构的 pause/resume/cancel 请求；Processor 与工具根据能力协商执行，不能假定旧 converter 支持新协议。
- Converter 停止派发新 Tile，等待在途单元到安全边界，刷新完成记录，发出暂停确认并按约定退出。
- Processor/ProcessManager 区分“已确认暂停的退出”“成功”“失败”“取消”，不能将任意非零退出都判为失败。
- 若 converter 当前输出是普通日志，不直接在混合 stdout 中猜暂停状态；新增受控事件通道或保证机器可读事件与日志分离。
- 用户在 pausing 时仍可取消；未到安全边界不能承诺立即暂停。大 Tile 导致的等待需明确显示。

### 数据库与 UI

- TaskStore 持久化暂停/恢复状态、检查点位置与摘要、兼容性和可恢复原因；已有任务没有检查点时按旧行为处理。
- `Processing.tsx` 显示“正在暂停、已暂停、继续、重新开始”；继续与重新开始必须是不同动作。
- 继续前原子获取任务运行权，防止双击、两个窗口或两个进程同时恢复同一工作目录。
- 重启后先检查状态与磁盘完成记录；只有具备有效检查点的任务才显示可继续。
- 暂停任务释放串行调度占用；是否启动下一个排队任务需明确产品规则，建议沿用正常队列推进。

### 分阶段覆盖

| 阶段 | 第一版方向 |
| --- | --- |
| 转换 | Tile 完成边界暂停，Tile 级续跑 |
| 重建 | 先在阶段完成边界暂停；后续按 Proxy 依赖扩展检查点 |
| 纹理 | 先阶段边界；文件级恢复需处理源纹理与编码状态，后续独立实施 |
| 校验 | 可在恢复时重跑，不强求保存校验过程 |
| 最终提交 | 短暂不可暂停窗口，成功后不能被迟到暂停改写 |

处于旧工具不支持细粒度暂停的阶段时，应显示“等待当前阶段完成后暂停”，或明确该阶段不支持。不得用强制挂起进程冒充持久续跑。

## 9. 交付顺序与阶段出口

| 批次 | 对应阶段 | 可交付结果 | 进入下一批的条件 |
| --- | --- | --- | --- |
| 1 | A | 参数可靠、设置可保存、有并发与耗时基线 | 实际线程数可核实，能定位失败样本或明确证据缺口 |
| 2 | B | 已定位并发缺陷修复、有界 Tile 调度 | 目标故障回归通过、正确性无退化 |
| 3 | C | 有测量收益的单任务提速 | 同数据耗时改善，内存/质量不退化 |
| 4 | D | 转换 Tile 检查点与 CLI 恢复原型 | 崩溃窗口、输入变化、双重恢复测试通过 |
| 5 | E | 桌面暂停/继续、转换阶段重启续跑 | 安装环境端到端验证，状态与磁盘结果一致 |
| 后续 | 扩展 | 重建/纹理细粒度恢复、多任务资源调度 | 根据使用频率与测量结果决定 |

批次 1 可以立即实施。批次 2 先诊断再确定修改范围；暂停功能依赖检查点，不能单独先上线按钮。正确性与资源预算在每批持续验收。

暂不给整体固定工期：并发根因尚未确认，converter 新协议和工作单元边界尚需验证。批次 1 完成后输出可复现基线，再估算批次 2；检查点原型通过后再估算完整暂停覆盖范围。

## 10. 实施前需要得到的答案

1. 用户失败样本能否在当前固定 converter 版本复现？并发数、压缩模式和崩溃栈是什么？
2. 处理时间主要消耗在哪个阶段？当前单线程重试占了多少比例？
3. 原生依赖能否在修复后安全多线程？进程隔离是否值得其额外内存成本？
4. 一个顶层 Tile 的最长耗时和内存是多少，是否满足可接受的暂停等待？
5. 检查点写入和恢复验证成本是多少？哪些参数变化必须使所有结果失效？

这些是开发中的验证任务，不要求用户先给完答案才能开始。优先利用现有数据和日志建立证据，缺少特定样本时再明确指出。

## 11. 工作范围与验证边界

产品仓库负责设置、协议、阶段编排、恢复校验、桌面状态、打包与测试；converter 仓库负责原生并发、Tile 调度、Tile 完成记录和控制接口。当前只读取过相邻 converter 源码，尚未修改或发布该仓库。

部署时按 runtime capabilities 确认新能力；更新固定 converter URL/SHA256 并在安装环境验证，避免新 UI 配旧工具。历史自动测试通过不证明本计划新能力已实现，本文编写阶段也未执行新的性能或崩溃实验。
